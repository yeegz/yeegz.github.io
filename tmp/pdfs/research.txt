Deep Research Report on yeegz.github.io
Executive summary
Your portfolio is already more distinctive than the average developer portfolio. It has a strong authored
identity: a custom visual system, personal photography, Arabic/English naming, location and coordinates, a
hand-built tone, custom sigils, and even a hidden interaction/game tied to your name. The site is also not a
generic template repository: the public repo is a small static-site codebase with hand-authored
 index.html , styles.css , script.js , images, a PDF resume, robots.txt , and sitemap.xml ,
with no visible package manager, README, or build pipeline in the root. That gives the site character, but it
also means the current one-page architecture will become harder to scale as soon as projects become
richer, more narrative, and more numerous. 1


The main opportunity is not to make the site “more animated.” It is to make it more revealing. Right now,
projects are concise and stylish, but only two of the four are externally clickable; two are presented as inert
case rows, and the sitemap contains only the homepage. The result is that the site communicates taste and
polish, but not yet enough evidence, process, trade-offs, or outcomes to make each project feel like a
memorable story. Reworking the Projects area into first-class, per-project case-study pages is the single
highest-impact change for uniqueness, credibility, SEO depth, and recruiter usefulness. 2


The Skills section is the second-biggest opportunity. Its current “Technical System” taxonomy is clean and
legible, but it reads as a classified list rather than something emotionally memorable. A better direction is
an interactive skill constellation / signal-board / holiday-lights system that feels native to the current
archive/specimen aesthetic. The best implementation choice is likely inline SVG first, because SVG is DOM-
accessible and can expose names through <title> , while <canvas> is powerful for motion but weaker
for accessibility unless you provide semantic fallback content. If you want a “Christmas-lights” effect, use
SVG or CSS for the default accessible version, then progressively enhance with JavaScript; reserve Canvas
only for an optional decorative layer. 3


Technically, the site already does some important things right: it has a skip link, semantic headings,
 prefers-reduced-motion handling, lazy-loaded images, canonical URL, Open Graph/Twitter tags, a
Person JSON-LD block, a permissive robots.txt , and a valid sitemap. However, the CSS and JS are
already fairly large for a one-page portfolio, external animation libraries are loaded from CDN, there is no
visible analytics integration, no responsive image markup, no visible build tooling, and no visible CI/
performance regression testing. The next version should keep the handcrafted feeling but move to a more
maintainable content-and-build architecture. If you want the smallest change, use Vite with modularized JS.
If you want the best long-term structure, use Astro content collections with GitHub Pages deployment via
Actions. 4


My core recommendation is this: preserve the current visual signature, but shift the site from
“portfolio landing page” to “personal product archive.” That means dossier-like project pages, a more
expressive skills visualization, a visible personal narrative, richer internal linking, lightweight analytics, and a
build system that lets you keep shipping without turning the codebase into one giant scroll-script. 5

Reworking projects into full case studies
The Projects section should become the backbone of the site. Today, it behaves like an attractive inventory:
title, kicker, short description, stack, role, platform, date, status. That is good metadata, but it is only the
first layer. For hiring and personal differentiation, every project needs to answer a deeper set of questions:
Why did this exist? What was difficult? What trade-offs did you make? What did you learn? What
shipped? What is still imperfect? Right now, the homepage summarizes those answers but does not
expose them. 16


I recommend turning each project into a case file with a reusable layout. This fits your existing archive/
specimen aesthetic better than a generic “project detail page.” Visually, think of each page as a dossier:
coded header, status stripe, summary card, evidence gallery, engineering notes, and final verdict.
Structurally, think of it as content-first, with metadata frontmatter or JSON driving the page. Astro content
collections are well suited for this because they add typed structured content and page generation without
forcing you into a heavyweight CMS, and GitHub Pages now recommends Actions-based deployment for
Pages sites.        17

Motion, accessibility, performance, code quality, and deployment

UI and motion direction

The current site’s motion language is already a core part of its appeal, so the goal should be refinement, not
escalation. At the moment, custom motion is spread across the hero, reveals, cursor, sigils, the portrait
treatment, and the hidden game, with GSAP/ScrollTrigger/Lenis enabling the larger choreography. That
system works because the content is still limited. As the site grows, motion should become more selective
and role-based: hero motion for identity, reveal motion for section entrances, microinteraction motion for
controls, and optional decorative motion for atmosphere. Not every surface needs to move. 31


A good next-step language would be:


     • identity motion in the hero only,
     • evidence motion on project pages only where it explains a feature,
     • system motion in the skills map and timeline,
     • and ambient motion reduced to subtle grain, glow, or pulse.

Performance and code quality improvements

The site already uses helpful primitives such as loading="lazy" , decoding="async" , explicit image
dimensions, and fetchpriority="high" on the hero portrait. Those are all solid choices. Keep them.

The next performance gains will come from delivery architecture, not from tossing more micro-
optimizations at the current page. The highest-value improvements are:


    1. Split content from choreography. Move project data into structured content files and break the
       current giant script into modules. The visible JS file is already 67.2 KB and the CSS is 44 KB. Even if
       the site still feels fast in practice, that architecture will become harder to reason about as you add
       project pages, filters, search, and more custom interactions. 46


    2. Adopt responsive image delivery. You already include widths/heights, but you do not yet publish

    3. Modernize image formats. The repo image directory still includes multiple .jpg and .png

       delivery. Keep PNG where transparency or workflow requires it, but convert photographic content
       and most screenshots to AVIF/WebP variants. 48


    4. Use content-visibility strategically for long off-screen sections once you add case pages or
       accordions. MDN notes that content-visibility: auto lets browsers skip rendering work until
       content becomes relevant, improving initial load. Use this carefully on long narrative sections, not on
       content needed immediately above the fold. 49


    5. Tighten font loading. You currently load four Google font families. web.dev recommends
       optimizing web-font loading and using font-display strategies to reduce blank text and layout
       shifts. If you rebuild, subset or self-host only the weights and glyph ranges you actually need,
       especially since your design depends heavily on typography. 50

Build tooling and deployment

For implementation, I see two realistic paths.


Path A: stay close to the current setup. Use Vite as the build tool, keep writing HTML/CSS/JS, split the
current script into modules, generate project pages from simple content files, and deploy the static output
to GitHub Pages with Actions. Vite is specifically designed as a fast build tool for modern web projects, and
GitHub Pages now recommends Actions-based deployment flows. 56


Path B: move to Astro. This is the better long-term option if you want real case-study pages, notes, a
search index, typed metadata, and a future blog without giving up static output. Astro content collections
are purpose-built for structured content sets, and the generated site can still deploy to GitHub Pages. 17


For deployment hardening, I recommend:


     • moving to a custom domain when ready,
     • verifying the domain in GitHub Pages,
     • and documenting deployment in the repo README. GitHub documents both custom-domain
       configuration and verification, and explicitly notes that verification protects against takeover
       scenarios. 57


SEO, content strategy, and reference patterns

SEO and portfolio narrative

At the SEO layer, your foundation is already solid. The site has a descriptive title, a substantial meta
description, canonical URL, OG/Twitter metadata, robots, sitemap, and a Person JSON-LD object. What is
missing is content depth and page granularity. The sitemap contains only the homepage, there are no
visible project detail pages, and current structured data focuses on you as a person rather than on the work
itself. Separate project URLs would immediately improve indexable surface area and let you target
meaningful long-tail queries around your projects, technologies, and product work. 58




                                                      13
For copy strategy, the site should shift from a general role description to a personal thesis. Right now, the
value proposition is “Flutter & Full-Stack Developer,” “Software Engineering Student,” and “I build mobile and
web products with clean engineering, modern interfaces, and real user experience.” That is good, but still
broad. A stronger narrative would emphasize your differentiators together: product-minded engineering,
motion-sensitive UI craft, bilingual identity, student-to-builder trajectory, and your interest in both polished
interfaces and more creative systems like WebGL and game work. 11


A more distinctive homepage copy stack might be:


     • Hero headline: “I design and build product interfaces that feel precise, personal, and alive.”
     • Subhead: “Software engineering student in Malaysia shipping mobile, web, and creative interactive
       work.”
     • Primary CTA: “Read case studies”
     • Secondary CTA: “View resume”
     • Tertiary CTA: “Open lab notes”

That still matches the current tone, but it is more specific and less interchangeable.


You should also improve the content model around headings and CTAs. Google’s title-link guidance notes
that Search may get confused when multiple headings compete for primary prominence. Once you add
project pages, keep a single clear h1 , match the visible main title with the page title, and make every
page’s primary action obvious: demo, code, contact, or read the story.    20




Social previews and structured data

Social previews are already implemented with Open Graph and Twitter metadata, including image and alt
text. That is a strong baseline, and the Open Graph protocol exists precisely to turn pages into richer shared
objects in social environments. The next step is to generate different preview cards per project page—not
one generic card for the entire site. 59


Once you have multiple pages, add:


     • ProfilePage -style markup on the homepage if you expand the personal profile role,
     • SoftwareApplication on relevant software project pages,
     • CreativeWork when a project is better treated as a broader artifact,
     • and possibly a WebSite node if you add internal search later.      60
